# Operations lab: аудит, MongoDB, резервирование и PITR

Вся инфраструктура находится **на одном сервере 83.147.192.229**, рабочий каталог `/opt/manufacturing-demo`. Публичный интерфейс только читает данные. Административные задания выполняет root через SSH/cron. Внешняя выгрузка отключена; исходящих заданий отправки копий нет.

## Что делает cron

Время **UTC**, по часовому поясу этого сервера. Летом в Израиле UTC+3, зимой UTC+2; cron не сдвигается вслед за израильским временем. Текущий серверный пояс проверяется `timedatectl`.

| Cron | Команда `ops.py` | Назначение |
|---|---|---|
| `5 * * * *` | `backup` | Каждый час в :05: логическая копия PostgreSQL, MongoDB и конфигурации |
| `20 1 * * *` | `base` | Ежедневно 01:20: физическая базовая копия PostgreSQL |
| `35 2 * * *` | `restore` | Ежедневно 02:35: восстановить последнюю логическую копию обеих БД в изолированных контейнерах и сравнить контрольные данные |
| `45 3 * * 0` | `pitr` | Воскресенье 03:45: восстановить PostgreSQL до именованной точки перед контрольным изменением |
| `*/5 * * * *` | `status` | Каждые 5 минут: состояние заданий, WAL, свободного места и свежести копий |

При занятой общей блокировке второй запуск пропускается и пишет сообщение в лог; он не запускает параллельное восстановление. Задания имеют тайм-ауты команд. Сообщения об ошибках доступны в логе и на дашборде; внешние email/мессенджер-уведомления не подключены.

Отдельно остаётся существующий **systemd timer** `manufacturing-demo-tls.timer`, проверяющий продление TLS каждые 6 часов с случайной задержкой до 20 минут. Это не cron: `systemctl list-timers manufacturing-demo-tls.timer`.

## Резервные копии и хранение

`backup` открывает транзакцию PostgreSQL `REPEATABLE READ READ ONLY`, экспортирует её снимок и передаёт его `pg_dump --snapshot`. Контрольные отпечатки заказов, позиций, отгрузок, оплат и число событий аудита вычисляются в **том же снимке**. Восстановленная БД сравнивается с ними. `roles.sql` содержит определения ролей, в том числе секретные хеши; как и конфигурация, он не доступен через web.

MongoDB копируется через `mongodump --archive --gzip`; затем проверяется отпечаток отсортированных документов после восстановления. Протоколы сейчас неизменны после инициализации. PostgreSQL и MongoDB **не образуют общий транзакционный снимок**: при появлении записывающей интеграции потребуется отдельная стратегия согласованности и версия/контрольная точка обмена.

Завершённой копией считается каталог с `manifest.json`; в манифесте размеры и SHA-256 файлов. Проверка контрольной суммы не заменяет восстановление. Незавершённые каталоги после ошибок сохраняются для диагностики, не используются для восстановления; оператор просматривает и удаляет их отдельно.

- Логические: последние 24 завершённые копии плюс последняя копия каждого из последних 7 представленных дней. Частые ручные запуски тоже входят в эти 24.
- Физические: последние 3 завершённые базы. WAL сохраняется начиная с первой нужной записи самой старой из них; удаляются только более ранние сегменты той же timeline. При смене timeline старые цепочки сохраняются для ручной проверки.
- `archive_timeout=300`: PostgreSQL периодически закрывает активный сегмент для архивации. Это целевой интервал, не гарантия нулевой потери и не SLA.
- `archive_mode=on`, сжатый `archive_command`. При ошибке PostgreSQL повторяет архивацию; рост WAL может заполнить диск. Сводка предупреждает о свободном месте менее 2 GiB, архиве более 4 GiB, ошибках заданий/архивации или логической копии старше 2 часов. Новые тяжёлые задания не стартуют при свободном месте менее 2 GiB.
- Копии и ключи доступны только root; каталог WAL принадлежит postgres. На текущем сервере архивы не зашифрованы отдельно от защиты файловой системы. Перед будущей внешней отправкой нужны шифрование, выбранный получатель и проверка доставки. Сейчас экспорт отключён.

Все копии на том же сервере: **потеря сервера может означать потерю основных данных и всех копий**. Здесь демонстрируется защита от логических ошибок и процесс восстановления, не disaster recovery на независимую площадку. Измеренная длительность теста — время данного сценария, не обещанный RTO компании.

## Команды оператора

```sh
cd /opt/manufacturing-demo
python3 deploy/ops.py backup
python3 deploy/ops.py base
python3 deploy/ops.py restore
python3 deploy/ops.py pitr
python3 deploy/ops.py status
cat /etc/cron.d/manufacturing-demo-ops
tail -n 60 /var/log/manufacturing-demo-ops.log
```

`restore` и `pitr` **не заменяют рабочую БД**. Контейнеры `ops-check-*` запускаются с `--network none`, без опубликованных портов, с лимитом памяти и отдельными томами. Проверки PostgreSQL и MongoDB последовательны. После проверки контейнеры и их временные тома удаляются. Если сервер/процесс аварийно завершился, оставшиеся `ops-check-*` проверяет оператор; нельзя удалять основные тома.

PITR берёт последнюю физическую копию, записывает уникальный маркер в `operations.restore_probe`, создаёт `pg_create_restore_point`, затем меняет маркер. После архивации WAL отдельный PostgreSQL запускается с `recovery_target_name` и `recovery_target_action=promote`. Проверяется прежний маркер и контрольные бизнес-данные, а в основной БД — сохранение последующего значения. Это восстановление до выбранной точки WAL; рабочие заказы не изменяются. Готового безопасного «отката production одной кнопкой» нет.

## Журнал изменений

`audit.events` хранит время записи, transaction ID, объект, ID заказа, действие, before/after JSONB, исполнителя, причину, согласовавшего и пользователя БД. AFTER-триггеры работают на `public.orders` и `operations.demo_orders`; строка аудита фиксируется или откатывается **вместе** с изменением. Запись без `app.actor`/`app.reason` отклоняется. Обновление без изменения значений событие не создаёт. До установки триггера история не восстанавливается задним числом. Другие таблицы этим аудитом пока не покрыты.

Учебные копии заказов 104, 108, 111 лежат в `operations.demo_orders`. Демо-команда меняет только срок копии №108:

```sh
python3 /opt/manufacturing-demo/deploy/ops.py audit-demo
```

В интерфейсе копии явно обозначены. Имена `Demo operator`/`Demo director` — учебные роли, переданные SSH-оператором, не аутентификация реальных сотрудников. Роль приложения не имеет прав записи. Superuser способен изменить журнал; это не tamper-proof или регуляторный аудит.

Публичные GET API: `/api/audit?order_id=108&entity=operations.demo_orders` (до 100 последних событий), `/api/operations` (обезличенная сводка). Время аудита фактическое, независимо от исторического месяца финансового отчёта. UI позволяет фильтровать последние события по заказу, объекту и дате.

## MongoDB: назначение и границы

База `quality`, коллекция `protocols`, 7 синтетических протоколов. Один документ на попытку: серийный номер, ID заказа, время, метод/версия, версия конфигурации, результат и массив измерений с единицами/пределами. Есть индексы `(order_id,tested_at)` и `(serial,tested_at)`, валидация обязательных полей. Для №102 доступны исходный тест, отказ после возврата и повторный тест после замены. Последний тест не отменяет предыдущий и не является разрешением отгрузки.

Инициализация: `deploy/mongo-init.js` выполняется официальным Mongo entrypoint **только на новом томе**. Пароли генерирует `python3 deploy/prepare-ops-env.py .env.demo`; повторный запуск сохраняет существующие значения. Роль `dashboard` имеет только `read` базы `quality`; root-учётная запись находится только в Mongo-контейнере/административном окружении. Приложение получает только reader-пароль. Mongo не публикует порт. Кеш WiredTiger 256 MiB, лимит контейнера 512 MiB.

GET `/api/protocols?order_id=102&as_of=2026-09-12` возвращает протоколы не позже выбранной даты и сегодняшнего дня. Отсутствие Mongo помечается явно и не блокирует продажи/PostgreSQL. История всех попыток показывается в карточке заказа и разделе здоровья. Это отдельный учебный кейс документной модели, не замена реляционным заказам и платежам; связи между БД не защищены внешними ключами.

На этом VPS используется ядро Linux 7.0.0. MongoDB 8 отказалась запускаться из-за известной несовместимости аллокатора с ядрами 6.19–7.0.13, поэтому выбрана MongoDB 7.0. Проверены запуск, чтение, резервирование и восстановление; ядро сервера не менялось. См. [официальное предупреждение MongoDB 8](https://www.mongodb.com/docs/manual/release-notes/8.0/).

## Установка и обновление

Инфраструктурные файлы оператор обновляет через SSH. CI/CD доставляет только приложение и проверяет разрешённый набор файлов. При добавлении `operations.py` обновлён allowlist в `/usr/local/sbin/manufacturing-demo-deploy`; архив CI не может сам менять этот обработчик.

Перед первым запуском сохранить старую конфигурацию и дамп, выполнить `prepare-ops-env.py`, создать `ops/wal` с владельцем postgres (UID из текущего контейнера), `ops/public` mode 755 и остальные каталоги root-only. Применить `db/migrations/08-operations.sql` через `psql -v ON_ERROR_STOP=1`. Пересоздать только `db` и `mongo` с новым Compose; включение `archive_mode` требует рестарта PostgreSQL. Основной том сохраняется.

После успешных ручных `audit-demo`, `backup`, `base`, `restore`, `pitr` установить расписание:

```sh
install -o root -g root -m 644 deploy/manufacturing-demo-ops.cron /etc/cron.d/manufacturing-demo-ops
install -o root -g root -m 644 deploy/manufacturing-demo-ops.logrotate /etc/logrotate.d/manufacturing-demo-ops
touch /var/log/manufacturing-demo-ops.log
chmod 600 /var/log/manufacturing-demo-ops.log
systemctl is-active cron
```

`touch` сохраняет существующий лог при повторной установке. Проверить конфигурацию ротации: `logrotate --debug /etc/logrotate.d/manufacturing-demo-ops`.

Локально PostgreSQL-аудит запускается вместе с обычным Compose. Mongo опционален:

```sh
python3 deploy/prepare-ops-env.py .env
docker compose --profile operations up -d mongo
docker compose up -d --build dashboard
```

Хостовые `ops.py`/cron предназначены для Linux VPS и не запускаются на Mac. Все пути и расписания выше относятся к серверу. Добавление этих инструментов не означает, что основная БД когда-либо заменялась восстановленной копией.
